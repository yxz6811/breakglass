# BreakGlass 后续发展策略与技术改造方案

> 对象：<https://github.com/yxz6811/breakglass>（`main` @ `af0c3c62`）

## 第一部分　现状总结

### 1.1 项目当前是什么

一个**零依赖、零构建、零注入**的 Chrome MV3 未打包扩展 + 静态展示站：把演示视频里的数学曲线变成视频上方原位、可拖参数的 SVG 图层，另有一条独立的本地 Node 视觉 reader。

技术事实（三条决定了后面所有技术选型）：

1. **扩展不注入任何网页。** `manifest.json` 无 `content_scripts`、无 `web_accessible_resources`，`permissions: []`、`host_permissions: []`。`extension/src/page/*.js` 是**扩展自带演示页**的普通页面脚本。全仓库 `chrome.` 只有 1 处。
2. **没有消息协议。** `postMessage` / `sendMessage` / `CustomEvent` 为 0 处；模块间靠 `window.BreakGlass.*`，对外契约是本地 HTTP。
3. **产品侧只有 SVG 2D。** WebGL/Three.js 只存在于展示站 `site/vendor/`。

## 第二部分　需要改变的问题

### 2.1 战略层：愿景跑在验证前面

**现象**：三批新想法（全几何 → 3D → 视频理解+粒子+分龄）都在把产品做大，而仓库还停在"第一条抛物线的证据都没产生"。

**代价**：你们在增加串联层数，却不改变任何一层的失败概率。四层各 50% 成功率，整体 6%。

**要改变的做法**：把"产出真实数字"作为当前唯一的推进方向。**用证据换方向，而不是用想法换方向。**

### 2.2 战略层：没有明确的时间线，导致无法排序

时间线是整个排期的唯一输入，但它至今未确定。没有它，"该做什么"无法回答——两周和半年的答案完全相反。

### 2.3 战略层：核心价值主张目前没有着落

宪法写的是"在 `<video>` 上方挂独立 overlay、不打断观看"，实现是"处理用户选择的本地文件"。**"帮你正在看的视频"和"帮你选择的文件"是两个不相交的产品。**

- 若承诺"能在真实网页工作"→ 必须新增 `content_scripts` + `host_permissions`，并面对 Shadow DOM / CSP / 跨域 iframe / 各家播放器封装，且这是**一次范围修订**（"零侵入"目前是**未经真实页面检验的假设**，不是已验证约束）。
- 若不承诺 → 应把 README 中暗示"支持真实网页"的表述改清楚，明确产品边界。

**二选一必须选，不能悬着。** 悬着的代价是：团队可能一直在优化一个不成立的边界。

### 2.4 治理层：一条硬缺口——003 的验收没有输入口

`alignment.js` 的采样函数签名是：

```js
sampleAlignment({ definition, parameters, scale, contentRect, samples = 9, readActual })
```

它**接受一个 `readActual` 回调**（"由外部告诉我实际画出来的点在哪"）。而 `page/main.js` 的 `publishAlignment` **故意不传**该参数——这是刻意的诚实设计（注释原文：「不把刚画的路径当成实测，所以不算相对画面的 2% 结论」）。

问题在于：**页面也没有任何设计好的途径让"实测值"进来**，它只暴露 `contentRect`。

结论：**SC-003/004/005 不是"缺工作量"，是"缺一个决定"。** 不决定，它们永远无法通过。三个选项：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A. 测试钩子 | 暴露 `window.__breakglassActualPoints`，验收时人工/脚本注入 | 简单，但要定义"谁算权威" |
| B. 独立测量脚本 | 截图 + 像素分析离线算偏差，不经过页面 | 最客观，但脱离产品 |
| C. 只写验收协议 | 把"人工量点"写进 quickstart，接受不可自动化 | 最省事，SC 永远无法自动通过 |

### 2.5 治理层：测试基线有 15 个以上"最新"数字

`node --test` 项数在文档中出现过：`14、96、102、118、137、182、189、209、264、285、355、368、462、556、585、621、626、673`。其中 **626、556、673** 都被不同文档当作"最新"引用。

**要改变**：建立唯一权威基线（含提交号、命令、范围），放在 `README.md` 顶部或独立文件。

### 2.6 工程层：`main.js` 已到临界，而规范禁止重构

`extension/src/page/main.js` **2608 行**、约 40 个模块级 `let`、约 90 个函数、约 40 处监听；IIFE 顶部解构**无存在性检查**——漏一个 `<script>` 标签整页静默失效。而 `AGENTS.md` §5 要求"不做无关的大范围重构"。

**要改变**：把"拆分以便继续演进"登记为**有明确收益依据的重构**，而不是"无关重构"。至少先加启动断言（十分钟，消除一个静默失效模式）。

### 2.7 工程层：reader 正在从"独立服务"长成"第二后端"

| 漂移现象 | 证据 |
| --- | --- |
| 单服务三个端点、六套错误码体系 | `/read`、`/geometry/read`、`/geometry/ask` |
| **无法独立部署** | 启动即 `require` 扩展的 `lesson/reading.js` 与 `geometry-scene/validate.js` |
| 真实识别与开发夹具**数据上不可分** | `read.mjs:207` 硬编码 `source:'preset'`、`:210` `equationId:'fixture.parabola'` |
| **Origin 白名单可绕过** | `server.mjs:80-81, 94`：只在**带** `Origin` 时校验；缺失即放行 |
| `READER_HOST` 无校验 | `settings.mjs:54`：可设为 `0.0.0.0`，暴露带密钥服务 |
| `/read` 的 413 直接 `destroy()` | `server.mjs:136-142`：页面只看到网络错误 |
| 预读预算与理论上限相等 | 8 帧 × 60000ms ÷ 并发 2 = 240000ms = `READER_BUDGET_MS` 默认值 |

### 2.8 工程层：四条具体缺陷（便宜且该尽快做）

### 2.9 文档层：过期与不一致（需清理，但**不建议再增加分析文档**）

已识别 31 处不一致，其中影响开工的几条：

- `docs/BreakGlass-tech-stack.md` 通篇过期（称"CI：无"、constitution 1.4.0、26 个测试文件）
- 全 5 个 spec 的治理版本引用落后（实际 1.10.0 / 1.8.0，引用多为 1.7.1 / 1.9.1）

**同时要说清**：工作区已有 5 份分析笔记（约 540 KB），仓库自身有 5.7 MB docs 与 47 个 spec 文件。**这个项目的问题从来不是"不了解它"，再多一份分析边际价值为零。** 本节的所有条目应该在实施 PR 里顺手改掉，而不是专门开一轮文档工作。

### 2.10 一个文化性问题：投入结构失衡

**治理文档 47 个 spec 文件 + 40 KB 宪法 + 5.7 MB docs** ↔ **约 8 000 行代码**、**1 star**、**1 fork**、**真实模型零次运行**。

要说公道话：这套文档的真实功能是**跨 AI 会话的上下文交接协议**——在靠 AI 反复接手、上下文会丢失的工作方式下，把"什么不能说、什么不许试"写进文件是理性的，甚至是流程能跑下去的前提。

但代价必须承认：**它同时锁住了迭代速度**。所以下面的排期原则是——**往"产生证据"倾斜，不再往"增加规格与治理"倾斜。**

## 第三部分　如果要做：三层拆分与完整技术方案

### 3.0 先纠正一个命名

团队说"AI 自动识别**全几何图形**"。**这个命名会导致排期与风险评估全错。**

差距不在 AI 能力，而在这些**纯确定性工程**：

| 需要造的东西 | 现状 |
| --- | --- |
| 统一的形状/图元 schema | 只有 `ParabolaDefinition` 一种 |
| 白名单求值器 + 参数域定义 | `evaluate.js` 只有一条注册项 |
| 每类形状的校验规则 | `validate.js` 全部围绕 `a/h/k` |
| 通用概念类型体系（`kind`） | `SceneResult` 只有 `right-triangle` |
| `CurveResult` 之外的通用来源/契约 | 005 的 `SceneResult` 不通用 |

**结论：这件事 80% 是重构与建模，20% 才是 AI。**

### 3.1 三层拆分（不要混着做）

| 层 | 内容 | 前置 | 性质 |
| --- | --- | --- | --- |
| **L1 识别层泛化** | 形状注册表、概念类型体系、通用校验 | 无 | 纯确定性重构，**所有事的公共前置** |
| **L2 预处理管线** | 离线抽帧 → 分段 → 概念标注 → 产出 `VideoTimeline` | L1 | 新架构，**替代实时约束** |
| **L3 表示层** | 粒子（WebGL）、分龄解析深度 | L2 的已确认产出 | 独立开关、独立验收、**需宪法修订** |

**顺序理由**：L3 的两种呈现都必须建立在 L2 的"已确认产出"之上；L2 必须建立在 L1 的概念类型体系之上。跳过 L1 做 L2 → 一堆没有 schema 的自由文本；跳过 L2 做 L3 → 又一个必须挂"尚未接通"标签的炫技功能。

### 3.2 为什么"预处理"是真正的架构解锁

现在的架构被实时性锁死：

| 现有约束 | 值 |
| --- | --- |
| 破壁保底 `fallbackAfterMs` | **1500 ms** |
| 当前帧单帧截止 | **30 000 ms** |
| 整段预读截止 | **300 000 ms** |
| 单帧上传 | 1 张 / 4 MiB 请求体 |
| 整段视频上传 | **宪法明令禁止** |

改成预处理后，**这些全部塌缩成一条："处理一支片子要多久"。** 没有 1500ms、没有超时回退、没有"点破壁才去请求"。

**直接后果（重要）**：`fallbackAfterMs=1500` 这个硬约束、`createWake`/`startCached` 双入口、以及原则 IX 为"显式单帧"打的一系列补丁，在预处理模式下**大部分变成不必要的复杂度**。这不是"加功能"，这是**架构简化**。

**而且这个方向已有雏形**：003 的开播前阅读就是"片子可播放即自行稀疏抽帧（≤8 处）、算完即用、失败丢弃"——那正是一条预处理管线，只是只问一个问题、只采 8 帧、还与播放抢时间。L2 的本质是**把 003 的模式从"8 帧试读"扩展为"整段结构化理解"**。

### 3.3 L1：形状注册表与概念类型体系

#### 3.3.1 形状注册表（`ShapeRegistry`）

把 `evaluate.js` 的单条注册表泛化为：

```js
// 形状定义
ShapeDef = {
  kind: 'parabola' | 'line' | 'circle' | 'sine' | 'ellipse' | 'hyperbola' | ... ,
  version: '1.0.0',
  parameters: {            // 参数域（替换现在硬编码的 a/h/k）
    a: { initial, min, max, step, label, unit },
    ...
  },
  evaluate(params, x) -> y | [y...],     // 单值/多值（圆、椭圆是多值）
  domain: { min, max },
  range:  { min, max },
  normalize(params) -> params,            // 规范化（如圆的 r 取正）
  validate(params) -> { ok, code?, message? },
  formula(params) -> string,              // 供界面显示
  dragParameter: 'a' | 'h' | ... ,        // 控制点拖动绑定哪个参数
  sampleHints: { discriminants: [...], asymptotes: [...] }  // 供采样补关键点
}
```

**要点**：
- **多值形状**（圆、椭圆）需要 `evaluate` 返回数组——这是现在 `readAt` 在 `figures.js` 里已经处理过的情况，可以直接上提。
- **关键点补采样**：`figures.js` 现在已经会为抛物线补顶点、为圆补 `0/π/2/π/3π/2/2π`、为正弦补整周期。这套逻辑必须随注册表一起泛化。
- **裁剪**：`figures.js` 已有 **Liang–Barsky**，泛化即可复用。
- `MAX_SAMPLES = 4097` 的上限保留。

**复用度评估**：`geometry/figures.js`（396 行）已经实现了四种图形 + 关键点补采样 + Liang–Barsky 裁剪，**约 60–70% 可直接上提为注册表基础设施**。这不是从零开始。

#### 3.3.2 概念类型体系（`ConceptKind`）

现在只有 `SceneResult.kind = 'right-triangle'` 和曲线侧的 `equationId`。需要一套分层的类型体系：

```
ConceptKind
├── 函数图像类        parabola / line / sine / exponential / ...
├── 圆锥曲线类        circle / ellipse / hyperbola
├── 平面几何类        right-triangle / general-triangle / circle-geometry / ...
├── 代数推导类        equation-transform / expansion / factoring / ...        ← ⚠ 最难，建议最后
└── 概念说明类        definition / theorem-statement / ...                     ← 无图形，只标时间
```

**建议**：前两类由曲线侧契约扩展；第三类已由 005 的 `SceneResult` 覆盖；**第四、五类先不做**——它们需要理解推导语义，是当前能力之外的东西。

**每类必须有**：校验规则 + 求值/几何算法规格 + 参数域 + 错误码。

### 3.4 L2：预处理管线

#### 3.4.1 流程

```
① 本地抽帧        固定间隔（建议 1 帧 / 1–2 秒），宽 ≤640，JPEG 0.72
② 帧去重          相似度阈值剔除近重复帧（板书停留时大量重复）
③ 分批打包        每批 N 帧（建议 8–16），带 videoId/time/frameSize/课程说明
④ 概念分段        每批问一次模型：这一段讲了什么概念、起止时间、类型、参数候选
⑤ 确定性校验      每类概念走自己的校验器（复用 L1 的注册表）
⑥ 合并时间轴      跨批去重、边界平滑、冲突消解
⑦ 输出产物        VideoTimeline（结构化 JSON）+ 逐概念置信度 + 丢弃原因
```

#### 3.4.2 帧采样策略（这是成本的主要决定因素）

一支 10 分钟视频的算术：

| 采样率 | 帧数 | 上传量（按 40 KB/帧） | 8 帧/批 | 批次数 |
| --- | --- | --- | --- | --- |
| 1 帧/秒 | 600 | 24 MB | 8 | 75 |
| **1 帧/2 秒** | **300** | **12 MB** | **8** | **38** |
| 1 帧/5 秒 | 120 | 4.8 MB | 8 | 15 |

**建议起点：1 帧/2 秒**。理由是数学课件的视觉变化频率低于 1 Hz（板书一笔能停十几秒），2 秒采样几乎不丢信息，但成本砍半。

**必须做去重**：板书停留会产生大量近重复帧，去重能再省 30–50% 的调用。

#### 3.4.3 两个必须提前定的技术选择

| 选择 | 选项 | 建议与理由 |
| --- | --- | --- |
| 计算位置 | 浏览器内 vs 本地 reader | **本地 reader**。浏览器内要装模型（不可能），或调用远程（密钥进浏览器，违宪）。reader 已经是"本地无状态服务"，天然是预处理服务 |
| 上传边界 | 只本机文件+自制素材 vs 覆盖在线视频 | **只本机文件+自制素材**。覆盖在线视频会同时踩版权与"整段上传"两条线，宪法需明确修订，且工程量约为前者三倍 |

#### 3.4.4 上游调用与成本

| 项 | 建议 |
| --- | --- |
| 每次调用 | 8–16 帧 + 该批时间范围 + 前一批的概念摘要（做上下文衔接） |
| 并发 | 复用现有 `READER_CONCURRENCY`（默认 2），但**预处理可以更高**（4–6），因为用户不在实时等待 |
| 重试 | 失败批次**允许有限重试**（1 次）——这与实时路径"不自动重试"的规则不同，需在契约里写明 |
| 预算 | 新增 `READER_PREPROCESS_BUDGET_MS`，量级应为**分钟级**（如 15 分钟），与现有 240 s 分开 |
| 成本上限 | **必须显示给用户**："这支视频约需 38 次模型调用，预计 X 元"——因为这是用户的钱 |

**这里有一个必须写进契约的诚实要求**：预处理是**批量、可失败、可部分成功**的。产物必须能表达"第 3–5 分钟识别失败，其余可用"，而不是整体成败。

### 3.6 L3-① 粒子化身：技术方案

#### 3.6.1 定位（这条必须守住）

> **粒子必须是"已确认几何"的另一种画法，不能成为"另一种理解"。**

若粒子由模型自由生成形状 → 同时丢掉确定性与诚实来源两条宪法支柱。
若粒子把**已校验的** `definition`（顶点、开口、定义域、关键点）用水滴/轨迹呈现 → 完全合法，且与 `figures.js` 的"本地数学探索"同级。

#### 3.6.2 技术路线选择

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 原生 WebGL** | 手写 shader + 点云 | 零依赖（符合现有纪律）、体积极小、可控 | 开发量大，需自写数学与生命周期 |
| **B. 引入 Three.js** | 复用展示站已有的 min 文件 | 开发快 | 产品侧首次引入运行时依赖（`three.module.min.js` 338 KB + `three.core.min.js` 381 KB），**违反"零依赖"当前基线**，需宪法修订 |
| C. Canvas 2D 伪粒子 | 2D 绘制 | 最省事 | 几千个粒子会掉帧，拿不到"实时操控"的观感 |

**建议：A（原生 WebGL）**。理由是它保住了这个项目最有价值的工程特征——零依赖、无供应链风险、`script-src 'self'`。粒子系统的数学（沿曲线采样、速度场、生命周期）不复杂，约 400–700 行可做出可用效果。

**但要诚实评估**：如果时间线紧，B 的 3–5 天能换来 A 的 2 周。这是一个**真实的取舍**，不是纯技术问题。

#### 3.6.3 粒子系统的必要设计

| 项 | 建议值 | 说明 |
| --- | --- | --- |
| 粒子数上限 | 4 000（桌面）／1 500（移动） | 按 `devicePixelRatio` 与设备能力自适应 |
| 目标帧率 | 30 fps（与展示站背景一致） | 复用 `FRAME_INTERVAL_MS = 1000/30` 的限帧经验 |
| 采样源 | **已校验的 `definition`** | 粒子位置由 `evaluate()` 决定，不由模型决定 |
| 交互 | 拖动参数 → 粒子沿几何重排（不是重新生成） | 保证"操控的是同一个对象" |
| 降级 | WebGL 不可用 / `prefers-reduced-motion` | 回落到现有 SVG 静态图 |
| 生命周期 | 页面隐藏停 rAF；退出即 `dispose()` 并释放 GL 资源 | 复用现有纪律 |
| 计时 | 独立埋点，**不得混入** P0 的 1500ms/100ms 指标 | 宪法已有此要求 |

**必须新增的预算**（现有宪法只有 P0/P1 两档，这是第三个）：

- 首次初始化耗时、缓存命中耗时（分开计时）
- 峰值显存目标
- 设备下限（明确"不支持低于 X 的设备"，并给出降级路径）
- 安全：不得加载远程 shader/纹理；只允许随扩展打包或经完整性校验的固定资源

### 3.7 L3-② 分龄解析：技术方案

#### 3.7.1 合法性判据（一句话）

> **解析必须基于已确认的几何对象，而不是自由生成。**

因为 AGENTS §19 与宪法明确禁止"生成 HTML、幻灯片、测验、语音或第二种曲线"。

| 做法 | 判断 |
| --- | --- |
| 同一份已确认几何，按年龄段调整**措辞、细节密度、类比** | ✅ 便宜、安全、可验收 |
| 按年龄段切换到不同**数学框架**（具体→抽象→形式化） | ⚠️ 那是三套内容体系，是内容工程不是功能 |
| 让模型自由"讲解这个视频" | ❌ 违反原则 III/VII，会产生无法校验的幻觉 |

#### 3.7.2 建议的数据模型

把年龄段做成**同一动作的表达深度**，而不是新系统：

```js
explain_change = {
  type: 'explain_change',
  sceneRevision: 3,
  depth: 'concrete' | 'standard' | 'formal',   // 新增字段，默认 'standard'
  audience: 'primary' | 'middle' | 'high' | 'undergrad'   // 可选，映射到 depth
}
```

**要点**：
- 数值必须**取自实际执行结果**（005 契约已有此要求：「解释中的数值必须取自实际执行结果」）；
- 三种深度共用同一份 `solveTriangle`/`evaluate` 输出，**只是模板不同**；
- 首版建议只做 `standard` + `concrete` 两档，`formal` 后置。

#### 3.7.3 如果要做"框架切换"（不推荐现在做）

那需要三套并行内容体系，且每套都要独立专家评审。工程量与前三层相加同量级，**建议明确记为"不在当前范围"**，避免被当成一个参数问题。

## 第四部分　建议的推进顺序

### 4.1 分阶段（与时间线解耦的部分）

**阶段 0：结掉"决定类"的事（不写代码）**

| 决定 | 为什么必须现在定 |
| --- | --- |
| **正式演示视频 + 冻结 `demo-parabola.json`** | 它卡住测量 → 卡住 P0 验收 → 卡住"再加一层"的合理性。**这是整个链路真正的瓶颈** |
| **`readActual` 的输入方式**（A/B/C 三选一） | 不选，SC-003/004/005 永远无法通过 |
| **产品边界**：承诺真实网页 vs 明确只做本机文件 | 悬着会导致团队优化一个不成立的边界 |
| **3D 与预处理的定位**：是替换还是增量 | 决定叙事是否重写 |
| **预处理素材范围**：本机文件 vs 在线视频 | 工程量差 3 倍，且影响合规 |

**阶段 1：产出真实数字（2–4 周）**

- 拿正式素材 → 做四画幅 2% + 热缓存 20 次 P95（T030/T038/T024）
- 真实模型跑 5–10 支真实课件视频，**写出错误率与失败模式**（不要求准，要求有数）
- 顺手做掉四条便宜缺陷 + reader 安全修复 + 唯一测试基线

**这一步的产出不是代码，是一张可信的能力表**，它同时解掉 9 项未完成里的 5 项。

**阶段 2：L1 形状注册表泛化（1–2 周）**

无论走不走预处理，这一层都必须做——它是"全几何图形"的真实内容，也是 L2 的前置。**并且它会在阶段 1 的真实模型测试中被迫建起来**（因为你会立刻遇到"只能识别抛物线"的限制）。

**阶段 3：L2 预处理管线（3–5 周）**

新建 `specs/006`，先做**只本机文件 + 自制素材**的版本。

**阶段 4：L3 表示层（2–3 周，可独立取舍）**

粒子与分龄解析**各自独立开关、独立验收**。可以先只做其中一个。

### 4.2 两种时间线下的取舍

**若 ≤ 2 个月：**

> 只做阶段 0 + 阶段 1，**暂停 L2/L3**。

理由：两个月里，把"一条抛物线 + 真实模型有数 + 正式素材 + 硬指标记录"做到可追问而不崩，比开三个半成品强。**明确砍掉 3D 与全几何**，并把砍掉的理由写进 README（诚实标注也是这个项目的纪律）。

**若 3–6 个月：**

> 阶段 0 → 1 → 2 → 3，**L3 视剩余时间取舍**。

粒子建议先做，因为它是**视觉冲击力最高、且不依赖模型准确率**的一层——它只依赖 L1 的确定性几何。分龄解析后做，因为它依赖 L2 的产出。

**若 ≥ 6 个月：**

> 全做，但仍建议**先 L1 再 L2**，并且把"3D 立体重建（真 3D，而非 3D 呈现）"作为独立研究方向单独评估——它与本文的 L3-①（把 2D 几何用粒子/3D 视角呈现）不是一回事。

### 4.3 必须坚持的三条纪律

1. **来源诚实不放松。** 预处理的产物必须能表达"哪一段是识别来的、哪一段是预设的、哪一段失败了"。粒子与分龄解析都不得暗示"已接通"。
2. **确定性门禁不放松。** 模型只产候选；形状、参数、时间轴全部要过校验器。粒子渲染的输入必须是**已校验**的几何。
3. **每加一层都必须独立验收。** 不允许"因为 3D 做出来了所以整个链路算通过"。

### 4.4 建议放弃或后置的

| 项 | 建议 | 理由 |
| --- | --- | --- |
| **3D 场景实时生成**（真 3D） | **后置到最末**，或改为"已确认几何的 3D 呈现" | 真 3D 与确定性门禁、零依赖、P0/P1 预算全面冲突；且它是换叙事 |
| 按数学框架切换的分龄解析 | **明确记为不在当前范围** | 三套内容体系，是内容工程 |
| 覆盖在线视频的预处理 | **除非有法务与版权结论，否则不做** | 版权 + 整段上传双重风险 |
| 继续增加分析/治理文档 | **暂停** | 边际价值为零，当前问题是缺证据 |
